多 Agent、记忆与评估

单个 Agent 会遇到三个瓶颈：任务太大一个上下文装不下；对话太长忘了前面的事；以及最根本的 —— 你怎么知道它做得好不好？ 本课是整个课程的最后一站。

01Orchestrator–Workers：一个领队，多个助手

任务：“调研 5 个开源大模型的参数量、上下文长度和许可证，整理成表格”。领队 Agent 把任务拆成子任务，分发给多个 worker Agent 并行执行（每个 worker 有自己独立的上下文），最后汇总。对比串行和并行。

并行能大幅缩短时间，但每个 worker 都要重新读一遍任务说明、各自搜索，总 token 数会明显更多。多 Agent 适合可以拆开、互相独立、信息量大的任务（如广度调研）；对强依赖、需要共享全部上下文的任务（如改同一份代码）反而容易出错。

03评估：pass@k 与 pass^k

LLM 的输出是随机的，同一个任务跑多次结果可能不同。假设某个 Agent 在一个任务上的单次成功率是 p：
pass@k = 跑 k 次至少成功一次的概率 = 1 − (1−p)^k —— 适合"可以多试几次、能自动验证"的场景（比如写代码有测试用例）。
pass^k = 跑 k 次每次都成功的概率 = p^k —— 衡量可靠性，适合面向用户的 Agent（客服不能十次里错一次）。

评估集要贴近真实使用场景；能用程序判定的尽量用程序（精确匹配、单元测试、检查最终状态）；开放式回答用 LLM 当评委，配一个清晰的评分标准，并抽样人工校验评委本身。
